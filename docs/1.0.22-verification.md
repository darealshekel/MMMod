# MMMod 1.0.22 Verification

Date: 2026-10-28. Scope: behavior-preserving source extraction and packaging of twelve supported client builds.

## Baselines and extraction

All twelve pinned released-source baselines were built and tested before extraction. Most came from checksum-verified release source ZIPs, not their historical tags, because several older tags pointed to the wrong source tree. `versions.json` records the inputs.

The extraction replaced 3,046 Java source/test copies with 1,041 owned implementations, removing 2,005 duplicate copies. An identical chat dictionary is also shared by the ten versions that originally included it. Original package/class names and loader boundaries were retained.

Before the release-version update, every one of the 3,910 compiled main classes matched its corresponding baseline SHA-256 exactly. The final build changes only one main class: LiteLoader `Reference` now reads an `unknown` fallback instead of a stale hardcoded version if its metadata property is missing. Packaged `mmm-build.properties` supplies the actual version. No gameplay implementation changed.

Existing tests were retained. Two source-location assertions now read the assembled source directory; the release-metadata assertion reads the actual Gradle version. The 1.21 baseline had a missing changelog heading; this documentation-only issue was corrected and the baseline rerun passed.

## Runtime checks

- Fresh, disposable game/home/application-data directories, synthetic offline identities and no linked MMM accounts were used. User worlds, launcher configurations and credentials were not copied or modified.
- A fresh PASS sentinel and matching log marker were required for a gameplay-harness pass. A zero process exit code alone was insufficient.
- The 1.21 harness covered instamine, cancelled attacks/external removal, server rollback, breaks longer than ten seconds, mixin auditing, scoreboard updates, chat typing and advancements.
- Other available harnesses exercised their version's scoreboard/snapshot/history, mining and UI paths. 26.2/26.3 additionally exercised collections, inventory book, settings, summary, rank and pinned HUD fixtures.
- 1.12.2 loaded the actual release LiteMod on Java 8 in both loader modes and reached render/tick initialization with no mixin/linkage startup failure. Forge selected the `searge` refmap context.
- 1.17.1 and 26.1.2 have no existing gameplay harness. Startup was observed and the isolated process deliberately stopped; this is not a full-feature PASS.
- External process deadlines bounded all client runs. The expected Realms error for the fake token does not indicate use of a real account.

A Gradle cache-lock timeout and smoke-launch path/guard configuration problems occurred during initial attempts. They were corrected or retried, and the accepted runs passed. They did not require changing production gameplay code.

## Packaging and build safety

Release checks validate embedded version, duplicate archive entries, expected class coverage, absence of smoke classes, and source/resource ownership. LiteLoader additionally verifies Java 8 class versions, license entries, and both `notch` and `searge` mapping contexts. Source archives include the shared files required to rebuild each wrapper.

Java 21 / Gradle 9.4.1 were used for Fabric 1.x builds; Java 26 / Gradle 9.7.0 for Fabric 26.x; Java 21 / Gradle 8.7 for LiteLoader compilation/downgrading. The independent core compiles with a Java 16 API target and runs its test harness on Java 21. The 1.21 runtime retry used Gradle 9.7.0 to avoid concurrent cache contention.

The extraction tool now preflights every destination and stores byte-exact originals plus a recovery plan before moving files. Shared resource assembly fails on missing resources or duplicate output paths. GitHub Actions runs the domain tests and all twelve adapter builds on future changes.

## Limits

No guarantee is made for every server, operating system, hardware combination or third-party modpack. Authenticated production website sync was deliberately not exercised. Most gameplay harnesses use Loom development classpaths; package contents are checked separately. Only the LiteLoader startup checks directly launch the packaged release mod. Existing compatibility/feature differences between Minecraft versions are retained.

Detailed local command logs, JUnit XMLs, before/after class maps, runtime markers and screenshots are kept under `build/verification`. Release asset hashes are provided in `SHA256SUMS.txt` and `manifest.json`.
